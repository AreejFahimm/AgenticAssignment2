GigBid: engineering design review (AI-4016 R&D report)

Author: your name / roll number · Repo: link · Live: link · Everything below cites evals/results/*.json (tables in Appendix A are generated from them) or a file in the repo. Read first (scope): all measurements use the offline profile (deterministic heuristics for analyst/risk/writer/critic, no LLM) on silver labels (rule-derived, not human-checked) over real Kaggle job posts + synthetic personas/clients. LLM-profile quality, live Upwork, Docker and Postgres were not run.

1. Problem and constraints

A freelancer loses hours scanning feeds, burns paid Connects on unwinnable jobs, sends generic proposals and meets scams (free work, off-platform payment, prompt-injection text). GigBid automates discovery, assessment and drafting; the human decides. Never automated: sending a proposal or message, spending Connects, accepting terms, contacting a client off-platform, claiming experience the portfolio does not show. Enforced by a LangGraph interrupt() that is the only path to the submit/send nodes (ADR 0002); there is no auto-send setting. Declared budgets (agent/config.yaml): p95 latency 15 s per job analysed and 30 s per proposal; USD 0.01 / 0.05 per job / proposal. Measured: Appendix A "Budgets" (0.65 s / 0.70 s p95 offline on a CPU laptop; USD 0 because no paid API was called, so these say nothing about LLM cost).

2. Architecture

Two durable hand-written LangGraph graphs (diagrams: docs/images/*.mmd, rationale per agent: docs/ARCHITECTURE.md). Bid graph (thread per job): Scout (dedup) → Analyst ‖ Risk ‖ Fit via Send → decide → Pricing → Writer → claim verifier → Critic (≤ 2 send-backs) → Compliance → dry-run preview → approval interrupt → submit (exactly-once keys). Conversation graph (thread per client conversation): Liaison (intent, reply, slots) → approval → send (+ tentative hold). One marketplace port (agent/marketplace_port.py) with a GigSim adapter (tested) and a live Upwork adapter skeleton (untested); agents only call MCP tools (Portfolio, Marketplace, Workspace servers; per-agent allowlists in agent/mcp_client.py). State / trace / memory are kept apart (ADR 0006): checkpointed state; JSON trace + audit log; long-term memory only through promotion_rules.py (style: ≥ 2 occurrences on ≥ 2 jobs; outcome: ≥ 3 samples per category). Stores: SQLite checkpointer (Postgres supported, untested), app DB, LangGraph store, in-process NumPy+BM25 index (no vector database). Frontend: React/Vite/TS with a client generated from FastAPI's OpenAPI.

3. R&D question A: tool granularity

Hypothesis (before running): BEST (rewritten, task-oriented descriptions) ≥ FINE (27 one-purpose tools) > COARSE (3 mega-tools); COARSE uses the fewest tokens. Setup: 40 tasks with known correct tool/arguments (evals/runners/tool_granularity.py); an offline embedding selector over tool names+descriptions (no LLM). Results (tool_granularity.json): BEST 0.80 selection accuracy (388 prompt-tokens of tool list), FINE 0.50 (232), COARSE 0.50 at server level only (52). Conclusion: description quality, not tool count, drives separability; coarse tools are cheap but their action argument is invisible to selection. Limits: this measures description discriminability, not agent behaviour; argument accuracy needs an LLM run and was not measured.

4. R&D question B: RAG

Variants implemented: V0 naive dense; V1 requirement decomposition; V2 hybrid BM25+dense (RRF); V3 cross-encoder rerank; V4 outcome-aware boost; V6 contextual chunks; V8 corrective RAG as a LangGraph loop (threshold calibrated on dev, checked on held-out: v8_calibration.json, F1 0.52 on held-out vs 0.0 at the default). Not built: V5, V7, V9. Hypothesis (before running): decomposition + hybrid + rerank raises Recall@5 over V0 by ≥ 10 points on jobs with ≥ 3 requirements. Refuted: best gained +1.9 points overall (0.369 vs 0.350) and lost MRR; hybrid alone (V2) and the outcome boost (V4) were worse than V0. Ablation (Appendix A, n = 112 jobs with gold evidence): removing the reranker improved Recall@5 (0.359 → 0.414): the MiniLM cross-encoder is out-of-domain for this corpus and costs ~1.5 s/job. The winning arm is decomposition + hybrid + contextual chunks, no rerank: Recall@5 0.511, MRR 0.633, nDCG@10 0.575 vs V0 0.357 / 0.527 / 0.413 (+15.4 points), at ~0.2 s p95 retrieval. That is what ships (rag.variant: ship). Caveat: contextual chunks expose the same skill metadata that defines the silver gold labels, so part of the gain is circular; the honest reading is "metadata-aware indexing helps when skills are implied rather than named", not "+15 points on real portfolios". By persona and job type: rag_retrieval.json / ablation.json slices (multi- vs few-requirement jobs show similar V0 vs best gaps; decomposition helped less than hypothesised). Where better retrieval did not help replies: in GigSim, V0, V2, best and ship reply rates are within noise of each other (Appendix A), because the simulated clients reward skill mentions and non-generic text, which every grounded variant provides; the large effect is grounded vs generic (control arm). Claim verification (B3): the offline writer is extractive, so natural drafts contain no fabrications. We planted 90 fabricated experience sentences into real drafts: all 90 removed; 0 of 104 true claims removed; unsupported-claim rate 0.51 → 0.00. This is an easy test (fabrications contain numbers/entities absent from evidence); paraphrased or partially true fabrications are not tested. Judge calibration: not done: needs the author's 30 labels (judge_calibration prepare/compute). No judge score is reported. Human pairwise panel: not run (pairwise_panel).

5. R&D question C: is multi-agent worth it?

Not answered as specified. The requested comparison (single ReAct agent vs langgraph-supervisor vs this graph) needs an LLM that chooses tools; none was run (agent_comparison.py contains the stubs). What was measured instead is an ablation of the graph's safeguards (agent_comparison.json, 57 jobs): removing the Risk Assessor lets 2 of 12 planted scams reach the approval screen (0 with it) and lowers bid/skip F1 0.552 → 0.516; removing verifier+Critic or Compliance changed nothing measurable offline, because the extractive writer never produces unsupported claims or contact details. So the evidence for multi-agent value here is the parallel risk veto and the approval architecture, not the Critic/Compliance loops, and a ReAct baseline might win on easy jobs: unknown.

7. Signature extension (X2: proposal experiments)

Two writer strategies (evidence-first vs concise+question) A/B-tested on the same jobs in GigSim with paired design, exact McNemar and bootstrap CI (docs/EXTENSION.md, Appendix A). Result: no significant difference at this sample size. The simulator is rule-based, so this validates the experiment machinery, not client behaviour.

9. Safety and platform respect

Enforced: untrusted text delimited/scanned/neutralised; nothing sent without an approval interrupt (auto-submitted jobs: 0 in every eval); unsupported claims removed; contact details/guarantees/off-platform asks stripped; PII masked in logs, traces and the audit log; OAuth tokens Fernet-encrypted; every query tenant-scoped; no scraping/browser automation/cookies. Injection results (Appendix A): the Risk Assessor flags 100% of the planted injections with defences on (0% off); the payload never reached the text to be sent in either mode because the offline writer is extractive, so this does not show the defence preventing harm. An attack that beats it: paraphrased instructions (2/10 detected). With an LLM writer that risk is real; the approval gate is the backstop. Upwork: live mode not exercised.
